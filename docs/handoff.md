# 零壹雲管家（Zerone Cloud）Prototype 交接文件

Nov 5, 2026（最後更新 Nov 11, 2026）

## 背景與目標

零壹要做三個網站，讓經銷商與終端客戶透過平台管理 Google Workspace（GWS）與 Google Cloud（GCP）。第一步是先做出可點擊的 Prototype，給使用者確認需求。

- 三個網站：管理端（零壹內部使用）、經銷商端、終端客戶端，三個都需要權限控管。
- 目前整合 GWS 與 GCP，之後會支援其他品牌與產品。
- 老闆的期限是 2026 年 12 月底前：零壹平台 GWS 上線、GCP 可以看到流量與用量、三個平台的 Prototype 完成。
- 本文件的範圍是 Prototype 的前端畫面，全部使用假資料。後端由 Terry 開發，API 格式尚未提供，之後再串接。
- 開發順序：先做管理端，再做經銷商端與終端客戶端。
- 介面語言：繁體中文。

## 已決定事項

以下是和使用者討論後已經定案的內容，Claude Code 可以直接照做。

- 平台名稱：中文「零壹雲管家」，英文「Zerone Cloud」。三個網站分別標示「Zerone Cloud · 管理端／經銷商端／客戶端」。（正式採用前需查商標與網域）
- 介面以現有的羽昇國際 SaaS 平台管理後台為基礎，不重新設計流程。
- 不做：刷卡資料管理、訂單管理。原本的訂單管理改成「執行單」。（方案管理原本不做，2026/11/10 會議決定加回來，見「GWS 訂單流程」一節）
- 營運端排程只保留「GWS 排程中心」。排程任務、TipTop 整合先不做（待使用者最後確認）。信件通知要做，但是否放第一階段還沒決定（2026/11/11）。
- 管理端選單分成：首頁、管理、產品、排程、系統。
- 執行單放在「管理」底下。
- 品牌管理、產品管理放在「管理」底下（不放在「產品」），畫面先出，內容之後再補。
- 使用者管理合成一頁，用篩選區分內部、經銷商、客戶。
- 客戶資料要標示所屬經銷商。
- 新增客戶時，網域欄位要做檢查（格式、系統內是否重複、Google 網域驗證）。
- 帳號與權限：零壹只幫每個經銷商、每個客戶開第一個帳號（對應現有的「組織管理員」角色），其他帳號與角色由他們自己建立。
- 執行單是業務的需求單：業務接到客戶需求後開立，簽核完由後勤處理客戶建檔、訂閱等工作。類型改為新訂、客戶轉入、續約、加購、中途升版（見「GWS 訂單流程」一節）。不提供取消訂閱（2026/11/11 確認）。是否列入第一階段上線範圍，之後再評估，但 Prototype 先做。
- 執行單流程：草稿 → 業務審核中 → 技術審核中 → 待處理 → 處理中 → 完成。簽核在系統內進行，多層依序為業務主管、技術主管（實際人選待定），任一關可以退回給業務修改後重送。只有「業務主管」角色能做第一關核准、只有「技術主管」角色能做第二關核准，後台管理員不能代為核准。
- 執行單的客戶依類型決定（2026/11/12）：新訂可以選新客戶或現有客戶（已經是平台其他產品的客戶）；客戶轉入一定是新客戶，要填客戶主檔「轉入客戶」的欄位（客戶資料、轉入後的經銷商、轉移備註），和訂閱無關；續約、加購、中途升版只適用現有客戶（選客戶與訂閱）。新客戶的主網域當場檢查格式與是否重複。核准後，新客戶的新訂由後勤在「新增客戶」建檔，客戶轉入由後勤在「轉入客戶」建檔並建立轉入，執行單內容會自動帶入。
- 核准後執行單列出處理步驟（新客戶先「建立客戶」，再送 Google）。後勤按步驟上的按鈕，執行單的資料會帶進客戶建檔或訂閱操作畫面；全部步驟完成，執行單自動變成「完成」。
- 後勤不一定要有執行單，也可以直接在 GWS 訂閱頁新訂、續約、加購、中途升版，以及從客戶管理轉入客戶。這些操作不經過草稿或簽核；依類型分成「排程執行」與「人工執行」（見「GWS 訂單流程」一節），畫面顯示處理結果。
- Google 失敗時可以重新送出，或改為「在 Google 手動處理」並填備註。手動處理的項目標示「待同步確認」，下次從 Google 同步時比對到結果才算完成。
- 轉移不需要轉移碼（2026/11/11 確認）。後勤在系統做轉入時，客戶已經在 Google 申請完移轉（申請時由客戶填代理商代碼與經銷商代碼），系統不需要顯示或輸入這些代碼。
- 所有 GWS 變更操作都要留下操作紀錄。
- 首頁是 Dashboard（重點數字卡片加圖表），內容含到期訂閱、近期執行單與 GCP 用量摘要。
- 權限上限：任何帳號都不能授予比自己更大的權限。
- 零壹可以替經銷商、客戶開帳號並管理其帳號（含停用、重設密碼）；經銷商、客戶也可以自己建立與管理帳號。
- 客戶詳情分成「組織資訊、客戶使用者、一般聯絡人、訂閱、執行單、異動歷程」六個分頁（2026/11/12 依參考畫面；參考畫面的「訂單」改為「執行單」，Tiptop 帳務資訊不做）。訂閱分頁只列出這個客戶的訂閱並連到訂閱詳情，訂閱的操作仍在「產品」底下。
- 客戶轉入的入口：客戶管理列表的「轉入客戶」，以及執行單的「客戶轉入」。「轉入客戶」頁可以選「新客戶」（建立主檔與第一個組織管理員帳號）或「現有客戶」（客戶已經在系統裡，例如其他產品的客戶：選客戶、選或輸入要轉入的 GWS 網域，完成後網域寫回客戶主檔）（2026/11/12）。客戶詳情不提供客戶轉入（2026/11/12 確認），只在有紀錄時顯示「客戶轉入紀錄」，用來查看或標記人工處理完成。GWS 整合預計使用 Cloud Channel API。
- 客戶轉移只做「轉入」，不做「轉出」。
- 「帳單」是獨立的權限項目（原待確認 #2，2026/11/10 確認）。
- 不做發票（Invoice）功能（原待確認 #8，2026/11/10 確認）。
- 視覺設計由 Claude Code 自行決定，不需沿用舊版 Prototype 的配色與版型。
- GCP 的客戶與經銷商資料第一階段不納入（2026/11/10 會議）。Prototype 畫面保留 GCP 相關頁面，標示「第一階段不納入」，用來和使用者討論。

## GWS 訂單流程（2026/11/10 後勤 × 後端會議）

與會：Connie、Terry、毛、Debbie。會議紀錄在 Notion「會議」資料庫。

**方案**：品牌管理、產品管理之外，把「方案」加回來。方案要有等級高低，系統用等級判斷升版或降版。

**訂單類型與執行方式**

| 類型 | 項目 | 執行方式 | 規則 |
| --- | --- | --- | --- |
| 新訂 | 全新客戶 | 排程執行 | |
| 新訂 | 客戶自己刷卡、要移轉進來 | 人工執行 | |
| 新訂 | 從其他經銷商移轉 | 人工執行 | 會議原寫「需由客戶提供移轉 ID」；11/11 確認不需要轉移碼（客戶在 Google 申請時自己填代理商代碼與經銷商代碼） |
| 續約 | 升版 | 排程執行 | 僅限現有客戶；續約不提供取消 |
| 續約 | 加人數 | 排程執行 | |
| 續約 | 降版 | 待確認（Terry） | |
| 續約 | 減人數 | 人工執行 | |
| 加購 | 加購人數 | 排程執行 | 只能加人，不能減人；期間一律到舊合約結束日 |
| 中途升版 | 合約未到期前升版 | 排程執行，待確認（Terry） | 可同時加購人數（只能加人，2026/11/12） |

- **排程執行**：送出後在「GWS 排程中心」建立一筆排程，到啟用時間由系統送 Google。續約排在舊合約到期日的隔天，新訂、加購、中途升版預設當天執行，可以改日期。
- **人工執行**：送出後狀態為「待人工執行」，後勤在 Google 後台完成後回系統標記並填說明，下次同步時比對確認。
- 不提供取消訂閱（原待確認 #19，2026/11/11 確認）。訂閱清單裡「已取消」的資料是 Google 同步回來的狀態。
- Prototype 的解讀：續約同時有多種變動時（例如升版又減人數），只要其中一項是人工執行，整筆就用人工執行。降版在 Terry 確認前先用人工執行。

**續約畫面**：顯示目前合約的起迄日期，版本、人數可以選，畫面標示升版／降版、人數增加／減少，並顯示會用哪種方式執行。

**加購**：只能加人數，期間到舊合約結束日，不能改。原本的「調整席次」拆成「加購」（只加）和續約時的減人數（人工）。

**排程衝突**：如果已經排了續約，在續約生效前又加購人數，系統要跳提醒，列出這個網域目前的排程，請操作人員先取消原本的排程，再重新按一次續約。

**客戶主檔**：一個客戶可以有多個網域；主檔要記錄負責業務，可以依「產品／新約或續約」指定不同業務。

**到期通知**：GWS 到期前 N 天寄信給負責續約的業務和後勤（天數待定）。

**減人數**：續約時的減人數由後勤在系統上人工執行；合約到期前由客戶端自行減人數，下一階段再做。

## GCP 需求（2026/11/11 與 Ray 的會議）

與會：Ray、Debbie。會議紀錄在 Notion「會議」資料庫。

- **待辦**：Ray 提供 GCP 的 API 憑證。
- **客戶建立**：建立客戶時經銷商 ID 必填，目前一律填羽昇；不能直接賣給客戶，客戶都要掛在羽昇底下。是否 GWS 也適用、「直銷（零壹）」要不要調整，待向後勤確認（#20），Prototype 先不動。
- **客戶轉移**：客戶在 Google 申請轉移時，要填「代理商代碼」（零壹）與「經銷商代碼」（客戶透過哪個經銷商購買）。**不需要轉移碼**（2026/11/11 確認）。後勤在系統做轉入時，客戶已經申請完畢，所以系統不需要顯示或輸入這兩個代碼。這取代 11/10 會議「需由客戶提供移轉 ID」的寫法。
- **新的 GCP 客戶**：由 Connie 到 GCP Console 開 billing account，讓客戶掛他們的專案（有時效性）。
- **費用明細**：GCP 費用以「專案」為單位彙總，可以往下展開看各服務的明細（管理端的 GCP 流量與用量、帳單明細都已改成這樣）。
- **權限是否細分到專案**：零壹管理平台不需要、經銷商平台不需要、客戶平台需要。
- **客戶網站（之後做客戶端時處理）**：費用用河流圖呈現；顯示剩餘可用量，接近上限時提醒；支援 spend cap／budget 設定；不呈現網路輸出；Gemini Enterprise（GE）是買席次、費用固定，超過額度才產生費用，只顯示費用意義不大，最好一併顯示用量與 token 數。
- **問答**：羽昇的資料庫在羽昇的 GCP（冠淳）。

## 角色與權限

三個網站共用同一套權限模型。原則是「零壹只開第一個帳號，其他由對方自己管」。

**組織與資料範圍**

- 零壹內部使用者：可以看到所有經銷商與客戶。
- 經銷商使用者：只能看到自己名下的客戶。
- 客戶使用者：只能看到自己公司。
- 資料範圍永遠由帳號所屬的組織決定，不可以只靠前端隱藏。後端必須再檢查一次，Prototype 只需模擬。

**帳號建立流程**

1. 零壹建立經銷商或客戶時，同時建立第一個「組織管理員」帳號。
2. 組織管理員登入後，在「使用者」和「角色管理」自己建立其他帳號與角色。
3. 新角色的權限以「資源等級」設定，每個資源選「禁止、唯讀、可編輯、可新增與編輯」。資源：客戶、經銷商、執行單、品牌與產品、訂閱、GCP 用量、排程、帳號、角色、系統日誌、帳單。
4. 畫面依登入帳號的角色顯示：「禁止」的頁面不出現在選單、直接開網址會顯示沒有權限；「唯讀」看得到資料但沒有新增、修改、送出的按鈕；「可編輯」才有按鈕。執行單的簽核另外依角色判斷（只有業務主管、技術主管能核准各自的關卡）。真正的權限檢查一定要在後端再做一次。
5. Prototype 的登入頁列出各角色的測試帳號，點一下就能用該角色登入，密碼不驗證。正式版不會有測試帳號區。

**零壹內部角色（已確認）**

- 後台管理員、業務、技術、PM、業務主管、技術主管、後勤
- 業務主管、技術主管負責執行單的兩關簽核；後勤處理核准後的執行單（客戶、訂閱可編輯），也負責 GCP 出帳與收款（帳單可編輯）。
- 經銷商與客戶各有一個預設的「組織管理員」角色（零壹建立的第一個帳號使用），其他角色由他們自建。

羽昇平台原有的 8 個角色（後台管理員、財務、銷售、工作人員：產品管理／技術／業務／業務 PickUp、組織管理員）只作參考，不沿用。

「帳單」是獨立的權限資源（經銷商可以分 Billing 來看）。（2026/11/10 確認）

## GCP 帳單（2026/11/10 新增）

- 流程：系統匯入上個月的 GCP Billing 費用並計算 → 後勤上傳 Google 帳單做「成本對帳」 → 確認並出帳（寄帳單給客戶的帳務聯絡人） → 標記已收款。已出帳且超過付款期限顯示「逾期」。
- 應收金額 = Google 費用 ×（1＋加成）× 匯率，四捨五入到元（TWD）。
- 成本對帳：依客戶比對 Google 帳單金額和我方計算。有差異的客戶要先處理才能出帳；處理方式二選一：採用 Google 金額（帳單成本改成 Google 的金額）或維持我方金額，並選差異原因、填說明。
- 「待確認」（還沒出帳）的帳單可以調整加成或備註；出帳後不能再改。
- 不開立發票，出帳後寄送帳單 PDF。
- 權限：看「帳單」頁需要帳單唯讀；出帳、收款、對帳需要帳單可編輯。預設後台管理員、後勤可編輯，業務、業務主管唯讀。
- 尚未做：經銷商分潤。

## 技術方向與做法原則

Prototype 階段的目標是「讓使用者點得動、看得懂」，之後要能接上 Terry 的後端，所以結構要一開始就分層。

- **語言與框架**：TypeScript 加 React（或 Next.js）。這是建議，如果 Terry 的部署方式（例如 Cloudflare Workers）有限制，再調整。
- **三個網站共用元件**：版型、表格、篩選列、狀態標籤、表單都抽成共用元件資料夾。管理端先做，經銷商端與客戶端再重用，只改選單和權限。
- **資料層分離**：假資料集中在一個資料層，頁面只透過函式取得資料。之後換成真的 API 呼叫時，頁面不用動。
- **權限**：Prototype 可以用一個「目前登入身分」切換器模擬不同角色看到的畫面。真正的權限檢查一定要在後端做，不能只靠前端隱藏按鈕。
- **寫入動作的假行為**：開立執行單、簽核、送出 Google、重送等動作，只在記憶體中改狀態並顯示提示，不需要永久保存。
- **範圍限制**：Prototype 不碰真實的 Google 帳號，不連線到任何 Google API。
- **之後上線需要的技術提醒**：GWS 排程需要真的排程器與失敗重試；GWS 整合預計用 Admin SDK 與 Cloud Channel API（待 Ray、Terry 確認）；GCP 費用預計從 Billing 匯出（BigQuery）取得。這些不在 Prototype 範圍內，只是讓 Claude Code 了解方向。
- **程式碼品質**：每頁寫完自己開起來看過（桌面 1440 寬，也要確認窄螢幕不會破版）。
